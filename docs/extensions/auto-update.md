# `auto-update` — the reminder that an update is waiting

Three pieces, deliberately separated:

| Piece | Runs | Does |
|---|---|---|
| `scripts/auto-update-check.sh` | cron, every 30 minutes | fetches `origin main`, counts the commits ahead, writes `~/.pi/agent/update-pending` |
| `extensions/auto-update` | session start | reads that file and puts one line in the system prompt |
| `scripts/update.sh` | you, or this module in `auto` mode | applies the update and deletes the flag |

Nothing in the first two moves your checkout. The thing that fast-forwards a tree is the thing that
prints the whole report and asks — that is `update.sh`, and it stays the only one.

## Why a flag file and not a check at session start

A network round trip on the session-start path is a session that hangs when the network does. The
check runs on cron, off the critical path, and leaves a small `key=value` file behind:

```
# Written by scripts/auto-update-check.sh. Delete this file to dismiss the reminder.
range=dc1f125e4a1b7c9d0f3a2b8c6d5e4f3a2b1c0d9e..444c3e9a7b2d1f0e9c8b7a6d5e4f3a2b1c0d9e8f
commits=3
checked=2026-08-28T09:30:04Z
```

Session start reads one small local file. If it is absent, malformed, or unreadable, the module does
nothing at all and the session starts normally — this is a reminder, and a reminder that can break a
session is worse than no reminder.

## What it injects

```
[update available] PiON has 3 new commits on origin/main (dc1f125..444c3e9).
Run `scripts/update.sh` to apply them. To dismiss this reminder, delete ~/.pi/agent/update-pending.
```

The block is delimited by `<!-- pi-config:auto-update v1 -->` markers and injected **once**: a
re-registration replaces the block rather than stacking a second copy, the same `injectOnce` /
`stripBlock` pair [session-context](session-context.md) uses.

All the I/O is in `session_start`. `before_agent_start` fires on every prompt and touches no disk.

## `prompt` versus `auto`

| `mode` | What session start does |
|---|---|
| `prompt` (default) | injects the line above; you decide when to run the update |
| `auto` | spawns `scripts/update.sh --yes` detached, and says so |

`auto` is a real trade, not a convenience toggle: it changes files under the checkout while a
session is starting against it. It is spawned through
[`runDetached`](../concepts/architecture.md) with a mutex, so two sessions starting together produce
one update, not a race — but a session started *during* the update still reads a moving tree. The
default is `prompt` for that reason.

## Configuration

`config/auto-update.json`, generated by the installer from `config/auto-update.default.json`:

| Key | Default | Alternative | If it is wrong |
|---|---|---|---|
| `autoUpdate.enabled` | `false` | `true` — cron checks, session start reminds | `false` disables the whole feature; the cron entry, if one exists, becomes a no-op |
| `autoUpdate.mode` | `"prompt"` | `"auto"` — apply without asking | an unrecognised value is reported once and treated as `"prompt"` |
| `autoUpdate.intervalMinutes` | `30` | `1`–`59` | anything else falls back to 30; the value is the `*/n` in the cron entry |

Only literal `true` enables it. A missing file, a missing key, `"true"` as a string, or JSON that
will not parse all mean off.

Set it through the installer, not by hand — the preference and the cron entry are installed
together:

```bash
./scripts/install.sh --section maintenance
```

## The cron entry

```
*/30 * * * * /path/to/pi-config/scripts/auto-update-check.sh >/dev/null 2>&1 # pi-config:auto-update
```

User-level, never system-level. The installer manages it as a read-filter-write on the marker
comment rather than an append, so adding, replacing and removing are one operation and a second
install run produces a byte-identical table instead of a duplicate. It is recorded as a `CRON` row
in the install manifest, so `scripts/uninstall.sh` removes it and leaves every other entry alone.

The redirect is not decoration: cron mails every byte a job writes, and a check that printed on
success would mail you 48 times a day.

## Running the check by hand

```bash
./scripts/auto-update-check.sh --verbose          # say what was found
./scripts/auto-update-check.sh --verbose --force  # check even when the preference is off
```

Every path exits 0, including the failures — cron does not retry, and a non-zero exit buys nothing
but a mail. The reason is written to `$XDG_STATE_HOME/pi-config/auto-update-check.log`, one line,
overwritten: "my auto-update stopped working" has to be answerable, and an expired credential, a
proxy and a laptop on a plane look identical without it.

!!! note "It counts, it does not compare"
    `HEAD != origin/main` is true on every feature branch ever created. The check asks
    `git rev-list --count HEAD..origin/main` instead — how many commits upstream has that you do
    not. On a feature branch cut from an up-to-date `main` that is zero, which is the honest answer.
