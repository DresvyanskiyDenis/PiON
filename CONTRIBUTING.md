# Contributing

Thank you for looking. This is a small repository with a strong opinion about a few things; the
fastest way to have a change accepted is to know which those are.

## Before you start

- **Read [Known limitations](https://dresvyanskiydenis.github.io/PiON/limitations/) first.** Several
  surprising behaviours are deliberate and already written down.
- **Open an issue before a large change.** A refactor of the composition root or a new extension
  module is worth agreeing on before it is written.
- Small, obvious fixes — a wrong default in the documentation, a broken link, a typo in a message —
  need no issue. Send the pull request.

## Setting up

```bash
git clone https://github.com/DresvyanskiyDenis/PiON.git
cd PiON
npm ci --ignore-scripts       # never without --ignore-scripts
```

Node ≥ 22.19.0 is required. There is **no build step**: the extensions are TypeScript executed by
Node's strip-only type loader, so nothing is emitted and nothing is bundled. That is also why a
module must not use any construct the strip-only loader rejects — TypeScript constructor parameter
properties are the one that has already bitten this tree.

For the documentation site:

```bash
uv run --with-requirements requirements-docs.txt mkdocs serve
```

## The checks

All three must pass, and CI runs them on every pull request:

```bash
./bin/pi-check --all      # 31 repository invariants
npm run typecheck
npm test
```

`bin/pi-check` is the interesting one. It fails on an unqualified model id, a tier bound to an absent
provider, any `fallback` / `failover` / `egressOrder` key, a secret-shaped literal in a tracked file,
an unreplaced `<PLACEHOLDER>`, a private file that became trackable, a vendored tree whose bytes no
longer match their recorded digests, and fifteen other things.

Exit `1` means the repository is wrong. Exit `2` means the checker could not run. Do not paper over
either.

> [!NOTE]
> Ten config files are **generated by the installer and git-ignored**, so a bare clone has only the
> `config/*.default.json` half. Rules that read one fall back to the template, so `--all` passes on a
> fresh clone with no install — do not "fix" a rule by copying a template into place, because that
> tests a tree no user ever has.
>
> Two rules are environmental rather than about your change: `PC-06` needs `git ls-files` and so only
> works inside a real checkout, and `PC-19` needs `--live` because it talks to the npm registry.

## Standing decisions

These are settled. A pull request that reverses one will be closed with a pointer here. Four of them
have a full [architecture decision record](https://dresvyanskiydenis.github.io/PiON/adr/) with the
alternatives that were rejected and why — read the relevant one before arguing.

| Decision | Why |
|---|---|
| **No provider failover, no silent substitution** | A result you cannot attribute to a provider is worse than an error. `PC-03` enforces it |
| **`guard` loads first, `trust` second, `doctor` last** | PI returns on the first `{block: true}` across extensions in load order. A call the guard blocks must reach the guard before anything rewrites its arguments |
| **The guard fails open on an internal error; hooks fail closed** | Whose bug is it? A bug in our gate must not blanket-block your machine. A declarative rule *you wrote* that silently stops applying **is** the bug |
| **Egress classes are declarative and are never described as a network boundary** | Nothing here intercepts a socket, and implied enforcement is worse than none |
| **`extensions/` is never symlinked into `~/.pi/agent/`** | PI would discover every module separately, in `readdir` order, and fail every one that has no default export |
| **No skills and no MCP server definitions ship** | The machinery ships; the content is yours. This is not an oversight to be fixed by adding "a few useful defaults" |
| **Nothing personal, no credentials, no tenant hostnames** | `PC-06` and `PC-12` fail the build. Use `<PLACEHOLDER>` or a `$VAR` reference |

## Rules for specific kinds of change

### Adding or changing a configuration key

- Change the **tracked template** (`config/<name>.default.json`), not only the generated file. Ten
  files are generated and git-ignored: `models`, `routing`, `mcp`, `settings`, `guard`,
  `trusted-roots`, `path-defaults`, `web`, `web-search`, `quota`. A change made only in the generated
  half does not exist for anyone else.
- Document it in the same pull request: what it does, the shipped default, a sensible alternative and
  who wants it, and **what breaks if it is wrong**.
- **Do not document a default you have not read out of the file or the code.** An invented default is
  worse than an omission, because it will be believed.

### Adding an extension module

- Export `id` and `register(pi)`. **Never a default export** — PI's loader treats a default export as
  an extension entry point, and the composition root is the only one of those in this tree.
- Add it to `ORDER` in `extensions/index.ts` and to `DECLARED_MODULES` in `extensions/lib/manifest.ts`
  at the position the load-order invariants require, and say in the pull request why that position.
- Decide fail-open or fail-closed explicitly, and write the reason in the module's header comment.
- No `*.test.ts` at the top level of `extensions/` — `PC-16` rejects it. Tests live in `test/`.

### Adding a repository rule

A new invariant belongs in `bin/rules/` as a rule module, not in prose. A rule that runs is worth ten
paragraphs that ask people to remember.

### Adding a dependency

Dependency count is not a disqualifier here — a reviewed package beats bespoke code. But:

- Record it in `config/packages.lock.json` **and** `docs/PACKAGES.md`. `PC-09` and `PC-18` check that
  the lock file, the ledger and `settings.json` agree, three ways.
- A rejected package goes in `docs/DENYLIST.md` with the reason. A rejection nobody wrote down gets
  re-proposed every six months.
- Licence must be compatible and a licence file must ship (`PC-17`).

### Changing vendored source

`pi-packages/` holds third-party code, patched deliberately. If you touch it:

- Keep the patch minimal and describe the behavioural difference from upstream.
- Re-record the per-file digests (`bin/pi-check --write-vendor-manifest`), or `PC-21` fails.
- Update [Third-party components](https://dresvyanskiydenis.github.io/PiON/reference/third-party/).

### Documentation

- Reference documentation lives in `docs/` and ships with the code that made it true. A broken
  internal link fails CI (`mkdocs build --strict`) — including a link into a heading that does
  not exist on the target page, which MkDocs only reports at INFO until `validation.links` in
  `mkdocs.yml` raises it. Read the build output rather than only its exit status.
- Recipes, FAQ entries and troubleshooting go in `wiki/`, which is pushed to the wiki repository
  separately — see `wiki/Publishing-This-Wiki.md`.
- English only. Concrete identifiers over prose. No marketing language.

## Commits and pull requests

- Conventional commits: `feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:`.
- Branch names: `feature/…` or `fix/…`.
- Keep the diff surgical. Every changed line should trace to the stated purpose; unrelated tidying
  belongs in its own pull request.
- The pull request template asks what an accident or an attacker can do after your change that they
  could not before. If a change touches the guard, hooks, trust or MCP, answer it.

## Reporting a security issue

Please do **not** open a public issue for a vulnerability. Use GitHub's private security advisory
form on this repository ("Security" → "Report a vulnerability"). Include the version, the
reproduction, and what an attacker gains.

Things that are *not* vulnerabilities here, because they are documented as out of scope: the egress
classes not being a network boundary, the guard not containing a process that already started, and an
allowlisted program that can execute other programs being equivalent to `allow-all`.
