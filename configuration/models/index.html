    config/models.json — providers and models¶

    Generated by the installer. Gitignored. Built from config/models.default.json plus the config/providers/*.json fragments you selected plus your answers. Hand edits are supported and expected; re-running the installer regenerates the file, so an edit that must survive belongs in config/providers/<id>.json or in config/models.default.json.

    Read by PI core, at startup. Symlinked as ~/.pi/agent/models.json.

    Shape¶

    {
  "providers": {
    "<provider-id>": {
      "baseUrl": "https://…",
      "api": "openai-completions",
      "apiKey": "$SOME_TOKEN",
      "headers": { "X-Whatever": "$SOME_VALUE" },
      "compat": { "…": "…" },
      "modelOverrides": { "<model-id>": { "contextWindow": 200000 } },
      "models": [ { "id": "…", "name": "…", "contextWindow": 200000, "maxTokens": 64000 } ]
    }
  }
}

    Two kinds of provider block, and the difference matters:

    Kind Example Rule
    Built-in — PI already ships the provider and its catalogue github-copilot Override the minimum. Re-declaring fields you did not mean to change is how OAuth blocks get destroyed. Use modelOverrides, not models.
    Custom — PI has never heard of it a self-hosted gateway, a server on loopback Declare it whole: baseUrl, api, apiKey, compat, and an explicit models array.

    PI's own catalogue knows more built-in providers than this harness ships a fragment for. That is not an invitation: a provider with no fragment has no prompts, no credential plan and no egress class, so it cannot be selected by the installer and nothing routes to it.

    Keys¶

    baseUrl¶

    The endpoint root. For an OpenAI-compatible server this normally ends in /v1; for a Chat-Completions surface exposed at a custom path, whatever that path is.

    baseUrl is NOT variable-expanded

    "$MY_HOST" in baseUrl is sent literally as the four characters $MY_HOST. Only apiKey and headers support $VAR and !command. A host that varies per installation is substituted at install time by scripts/install.sh from your answer — that is the entire reason the provider fragments have prompts.

    What breaks: an unexpanded variable produces a DNS failure whose message names a hostname you never typed. Omitting baseUrl on a built-in provider is correct and normal; omitting it on a custom one leaves PI with no endpoint at all.

    models.json's baseUrl is now the only one

    An extension used to re-register a loopback provider at runtime, and PI's provider composer resolves extension?.baseUrl ?? config?.baseUrl — so that extension's URL outranked this file. It was deleted with the local lane (owner decision, 2026-08-15), and nothing in extensions/ declares a baseUrl any more. What this file says is what is used.

    api¶

    The wire protocol. Set it only for a custom provider.

    Value Use for
    openai-completions the classic /chat/completions surface most self-hosted and gateway servers expose
    openai-responses OpenAI's Responses API
    anthropic-messages Anthropic's Messages API

    What breaks: setting api on github-copilot breaks it. Copilot dispatches three different wire APIs depending on the model, and PI picks the right one from its own catalogue. Pin it to one and the models on the other two stop working.

    apiKey¶

    A reference, never a value. bin/pi-check rule PC-06 fails the build if a key-shaped string is committed.

    Form Resolves to
    "$VAR" / "${VAR}" the environment variable
    "!some command" the command's stdout — re-executed on every request
    "$$" / "$!" a literal $ / !
    anything else itself, literally

    apiKey must be present and must resolve, even when the endpoint checks nothing

    Measured, not theorised. A provider block with no apiKey key at all is read as unconfigured, and PI drops that provider's entire catalogue from /model, Ctrl+P and --list-models. Every tier bound to it then fails to resolve. That reads as a broken harness rather than a missing credential.

    A present-but-unresolvable reference ($VAR for an unset variable) is a weaker failure: the models stay listed and the first request fails loudly. Still wrong, easier to diagnose.

    For a loopback server that authenticates nothing, ship a literal inert string — "not-required" — rather than omitting the key. PI treats a provider with no resolvable credential as unavailable, so an endpoint that genuinely needs none still has to say so.

    !command has no TTL

    PI re-executes a command credential on every LLM call. An unwrapped <cloud-cli> auth token costs one OAuth round trip per request. Wrap it in a small TTL cache (config/bin/dbx-token-cached is the worked example) and reference the wrapper. A keychain read belongs in config/shell/pi-env.sh, where it costs one read per shell, not one per request.

    headers¶

    Extra request headers. Supports the same $VAR / !command expansion as apiKey.

    Never set or rewrite X-Initiator on a Copilot-style provider

    GitHub's premium-request meter keys on it. bin/pi-check rule PC-15 fails the build if any extension references the header, and that rule exists because getting it wrong changes what you are billed rather than whether the request works.

    compat¶

    Per-provider (and optionally per-model) capability flags. Each one maps to exactly one observed failure. These are measured, not guessed.

    Flag Ship as Symptom when wrong
    supportsDeveloperRole false for most non-OpenAI OpenAI-compatible servers HTTP 400 on every request complaining about role developer
    supportsReasoningEffort false unless the server models it HTTP 400 on reasoning_effort
    supportsUsageInStreaming false for llama.cpp-class servers HTTP 400 on stream_options, or no usage at end of stream
    supportsFinishReason false when the server omits it The turn never ends. PI waits forever and it presents as a hung agent, not an error
    maxTokensField "max_tokens" for legacy surfaces HTTP 400 on max_completion_tokens
    thinkingFormat per model — "qwen-chat-template", "chat-template" the thinking toggle is silently ignored
    cacheControlFormat leave unset unless the endpoint really surfaces cache breakpoints reported prompt-cache savings that do not exist
    supportsStrictMode leave unset if strict JSON-schema tool mode is rejected occasional malformed tool JSON — a model-quality problem, not a config one

    The procedure for a new endpoint

    Start with everything off and maxTokensField: "max_tokens". Get one successful turn. Then enable one capability at a time. Turning a flag off that was needed costs a feature; turning one on that is unsupported costs an HTTP 400 on every request.

    Write what you measured into the fragment's notes[]. The next person cannot re-derive it from the config alone.

    modelOverrides¶

    A correction table for a built-in provider's bundled catalogue. One line per model.

    "modelOverrides": {
  "claude-opus-5":    { "contextWindow": 200000 },
  "claude-opus-4.5":  { "contextWindow": 168000 },
  "claude-haiku-4.5": { "contextWindow": 136000 },
  "gpt-4.1":          { "contextWindow":  64000 }
}

    This is the only per-model lever PI exposes, and correcting contextWindow is the single most valuable configuration change in this repository. The rule:

    contextWindow = min(200000, what the endpoint actually serves)

    What breaks if you get it wrong: over-declaring means compaction never fires before the request is already larger than the endpoint accepts, and the request is truncated upstream, silently. Under-declaring only compacts earlier than strictly necessary. The asymmetry is the whole argument. The full reasoning, the measurement recipe and the /context verification are on Context windows — read that page before changing a number here.

    An override for a model the endpoint does not serve is inert. It is safe to write the whole table.

    models¶

    An explicit catalogue, for a custom provider only. Each entry:

    Key Meaning
    id the exact string the endpoint expects on the wire
    name the human label in /model. Purely cosmetic
    contextWindow what the endpoint actually serves. For a local server, the -c / --ctx-size it was launched with, not the model's native window
    maxTokens output cap
    reasoning true for a thinking model
    thinkingLevelMap which reasoning efforts this model actually serves. See the warning below — the default when you omit it is not "all of them"
    input ["text"] or ["text", "image"]
    compat per-model overrides of the provider block, e.g. thinkingFormat
    samplingParams merged verbatim into the request body — temperature, top_p, top_k, min_p, repeat_penalty, and anything else with no first-class PI field

    Model ids are not guessable

    On a self-hosted serving platform they are your own endpoint names. On llama.cpp they are usually the model filename; on a swapping router, its alias; on Ollama, name:tag. Ask the server:

    curl -s "<your-base-url>/models" | jq -r '.data[].id'

    Do not copy ids out of anyone else's configuration — including the examples shipped in config/providers/openai-compatible.json, which are labelled example-… precisely because they do not exist anywhere.

    Dashes here, dots there

    The same model can carry two id conventions on two providers — databricks/databricks-claude-haiku-4-5 and github-copilot/claude-haiku-4.5. Getting it wrong produces model not in the registry at dispatch, which is loud but confusing the first time.

    A thinking model at the wrong temperature looks like a harness bug

    Use the values the model card publishes in samplingParams. Degradation from bad sampling presents as the agent being stupid, and you will look for it in the wrong place.

    An absent thinkingLevelMap is a claim, not a blank

    A reasoning: true model with no map is read as serving off, minimal, low, medium and high, and not xhigh or max. So omitting it advertises five levels in the model menu whether or not one of them ever reaches the wire — and if the provider's compat.supportsReasoningEffort is false, none of them does.

    Write the map when you know: null for a level the model does not serve, the wire value for one it does. All-null is the honest entry for a model whose thinking cannot be steered — it is not a claim that the model does not reason, and it makes any requested level clamp to off, which sends no parameter at all. That is the same wire as an absent map, correctly described.

    Do not widen a map because a curl returned 200. An OpenAI-compatible server will accept every reasoning_effort value it recognises while the provider transmits none of them. What the endpoint accepts is not what your provider sends. When a level is requested that the map does not serve, the dispatch says so — see onThinkingClamp.

    Provider fragments — the installer's source of truth¶

    config/providers/*.json are self-describing templates: the block that goes into models.json, the questions the installer must ask, the credentials needed, the egress class, the concurrency cap, and — importantly — the notes[] that JSON cannot carry as comments.

    Six ship:

    Fragment Built-in to PI? Egress Notes worth reading before you touch it
    github-copilot.json yes public Never run /login on this path — the OAuth resolver silently overrides your baseUrl
    databricks.json no confidential Model ids are your own serving-endpoint names; the compat block is measured
    openai-compatible.json no you choose Any gateway serving its own model names. The context window and the egress class are answers, not facts about the URL

    The fragment schema, the substitution rules and the merge algorithm are documented in config/providers/README.md, which is the contract between the fragments and the installer. To add a fourth provider, see Adding a provider — but check first whether openai-compatible already covers your endpoint.

    Verifying a change¶

    bin/pi-check --all             # PC-01 qualified ids, PC-02 tier resolution, PC-06 no keys, PC-10 no placeholders
pi --list-models               # does the provider appear at all?
pi -p 'reply with OK' --model '<provider>/<id>'

    Then, inside an interactive session, /context — it prints the resolved contextWindow and where that number came from, which is how you confirm an override landed.
