    config/mcp.json — MCP servers¶

    Generated by the installer. Gitignored. Built from config/mcp.default.json, which ships:

    { "mcpServers": {}, "settings": { "hostConfigDiscovery": "off", "directTools": false } }

    No MCP servers ship with this repository. They are per-user by nature — they carry your credentials, your hosts and your tool surface. What ships is the machinery: the vendored adapter, the project trust gate, the environment-minimising stdio wrapper, and the approval ledger. Read this page before you expect a server to start, because the defaults are deny-shaped and that is intentional.

    The installer's MCP step offers exactly two servers from config/mcp.example.json — context7 and playwright — and defaults to neither. The example file carries a third entry, lightpanda, which the installer deliberately does not offer: unlike the other two it needs its own binary on PATH, and a numbered option that writes a server entry pointing at a command you do not have produces a broken roster rather than a working one. Install it yourself, then copy the entry. Whatever you pick is written here. If config/mcp.json already exists when you re-run, the step stands down entirely and says so: the file is yours and the installer will not edit it.

    Hand edits are therefore safe. What a hand edit does not survive is a fresh clone, where only the .default.json half exists — so a server you want on every machine belongs in config/mcp.default.json as well.

    config/mcp.example.json is a template that is never loaded. Copy entries out of it.

    Server entries¶

    HTTP server¶

    "context7": {
  "url": "https://mcp.context7.com/mcp",
  "headers": { "CONTEXT7_API_KEY": "${CONTEXT7_API_KEY}" },
  "lifecycle": "lazy",
  "directTools": true
}

    stdio server¶

    "playwright": {
  "command": "mcp-stdio-guard",
  "args": ["npx", "-y", "@playwright/mcp", "--headless"],
  "env": {
    "MCP_STDIO_EXTRA_ENV": "PLAYWRIGHT_BROWSERS_PATH",
    "PLAYWRIGHT_BROWSERS_PATH": "${HOME}/.cache/ms-playwright"
  },
  "lifecycle": "lazy",
  "directTools": true
}

    Two browser lanes, split by output¶

    A headless-JS server and a full browser look like two ways to do one job, and declaring only the second looks like sensible deduplication. It is not: it deletes the cheap lane and makes every JavaScript-for-text page pay for a Chromium spawn.

    Lane Example server Answers Cannot
    text lightpanda goto, then markdown / tree / links / extract — real V8, no rendering produce a screenshot, ever; it draws nothing
    visual playwright screenshots, layout checks, visual diffs, full interaction —

    Split them by output, not by capability, and say so in AGENTS.md — otherwise a model with both enabled will pick whichever tool name it saw first. Both should be lazy: declaring the pair costs one config block and zero processes until a tool is actually called.

    "lightpanda": {
  "command": "mcp-stdio-guard",
  "args": ["lightpanda", "mcp"],
  "lifecycle": "lazy"
}
    Key Meaning
    url HTTP transport
    command / args stdio transport. Put mcp-stdio-guard first — see below
    headers ${VAR} expansion. Credentials go here as references, never as values
    env environment for a stdio child
    lifecycle lazy starts the server on first use instead of at session start
    directTools per-server override of the global setting

    Wrap every stdio server you did not write yourself

    A stdio MCP server is a child process that inherits your environment — every API key, every token you have exported for anything else. config/bin/mcp-stdio-guard re-execs the real command through env -i with an explicit baseline allowlist:

    HOME LOGNAME PATH SHELL TERM USER LANG LC_ALL TMPDIR
NODE_EXTRA_CA_CERTS HTTPS_PROXY HTTP_PROXY NO_PROXY https_proxy http_proxy no_proxy

    Anything else the server genuinely needs is named explicitly in MCP_STDIO_EXTRA_ENV, as the playwright example does. That is the whole mechanism: an allowlist you can read in one line, not a denylist you have to keep current.

    Omitting the wrapper is not a small convenience. It hands your entire credential set to code installed by npx -y.

    settings¶

    hostConfigDiscovery¶

    Ships "off".

    Other agent tools on the same machine keep their own MCP server lists. hostConfigDiscovery decides whether PI adopts them. "off" means: everything you get is what is written in config/mcp.json, and nothing appears because some other program on your laptop knows about it.

    Who would change it: somebody who genuinely wants one canonical MCP list maintained elsewhere.

    What breaks: turning it on makes your tool surface a function of software you did not configure here, changing under you when that other tool updates. It also silently widens what the agent can reach, which is exactly the class of change that should be visible in a diff.

    directTools¶

    Ships false.

    false routes an MCP server's tools through a single namespaced entry point. true flattens them into the top-level tool list.

    Who would change it: set "directTools": true per server for the two or three whose tools you use constantly — flattening makes them cheaper for the model to reach and better described.

    What breaks: flattening everything inflates the tool schema, which is part of the preamble on every request. A dozen MCP servers flattened is a permanent context tax you pay per turn and notice as a mysteriously large preamble in /context. Per-server, not globally.

    The project trust gate¶

    The vendored adapter carries a local patch at getConfigSources(): a server defined by a project — .mcp.json or .pi/mcp.json inside a repository you opened — is dropped unless it has been approved, keyed on the project path and the sha256 digest of those files.

    pi-mcp-approve <project-dir>            # show the config, then confirm interactively
pi-mcp-approve <project-dir> --yes      # approve without the prompt, for a scripted install
pi-mcp-approve --list                   # print the ledger
pi-mcp-approve --status <project-dir>   # current verdict, changes nothing

    The ledger is ~/.config/pi-config/mcp-approvals.jsonl, mode 0600, append-only; the last line for a directory wins. To revoke, delete the matching line.

    Being in a trusted root grants the right to RUN there, never to DEFINE MCP servers

    config/trusted-roots.json and this ledger are separate gates on purpose. Cloning a repository into a trusted root must not silently authorise it to spawn processes on your machine with your environment. Approval is per project and per content digest: if the project's MCP config changes, the approval no longer matches and it is denied again.

    Exit codes: 0 approved / clean, 1 refused or aborted, 2 the tool could not run.

    Why the adapter is vendored in-tree¶

    pi-packages/pi-mcp-adapter/ is third-party source committed into this repository rather than installed into node_modules/, and the reason is the patch above. The upstream package resolves its config sources in a way that cannot be intercepted from outside the module — there is no hook, no option and no wrapper position that sees project sources before they are merged. The gate has to live inside getConfigSources() or it does not exist.

    Vendoring makes that patch visible in a diff and re-applicable on every version bump, instead of being a postinstall script rewriting somebody else's code. Full attribution, licence and the patch's behavioural difference from upstream: Third-party components.

    Verifying a change¶

    pi-mcp-approve --list        # what the ledger says

    In a session, /doctor's D-07 reports any MCP server name mentioned in instruction text that is not declared in config/mcp.json — the usual cause of "why can't the agent see my server".

    A lazy server that has never been used has never been started, so its absence from the tool list until first use is expected, not a fault.
